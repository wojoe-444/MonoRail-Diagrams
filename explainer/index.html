BPMN 2.0 · DMN · MonoRail Diagrams

From process to diagram

How MonoRail describes a process or a decision: BPMN for flow, DMN for rules. Each example below is a real file in the repository, drawn by the repository's own tools from a short written brief, in whichever style you prefer.

Diagram style

Which notation?

BPMNDoes it happen over time?Steps in order, waiting, messages between participants, repeats, time limits.
DMNIs it facts in, answer out?Rules with no order and no side effects: given these inputs, what is the outcome?
BothA process that contains such a rule?The process asks the decision, then branches on the answer.

They connect in one way only: a business rule task asks a decision, and an exclusive gateway routes on its answer. A gateway that tests one fact with two outcomes stays in the process. One that tests several facts, or has more than two outcomes, becomes a decision.

Poem loop

BPMNexamples/poem-loop/
Question
how does a script improve a writing prompt with three separate agents?
Notation
BPMN (steps in order, three rounds, messages to another program)
Participants
Python script (drawn in full); Codex CLI (black box)
Outcomes
Prompt improved, after three rounds.
Decisions
none. The round count is fixed, so it is a loop marker, not a gateway.

What to notice

  • The Python script is a pool we draw in full. Codex is a black-box pool: we only exchange messages with it, so its insides are not drawn.
  • Each task sends a request (left dashed line) and gets a reply (right dashed line). That is one task with two message flows, not two tasks.
  • The circular arrow on Round means repeat. Three rounds is a fixed count, so there is a loop marker and no gateway.
  • The cylinder is a data store: the writer prompt outlives one round. The reviser overwrites it and the next round's writer reads it.

Chat turn

BPMNexamples/chat-turn/
Question
what happens to one message the user sends in Chat, from "Send" to the end of the turn?
Notation
BPMN (steps, a time limit, an interruption by the user)
Participants
MonoRail app (drawn in full); User (black box)
Outcomes
Turn finished, Message refused, Turn timed out, Turn stopped.
Decisions
"Chat already running a turn?" tests one fact with two outcomes, so it stays in the process.

What to notice

  • The envelope in the start circle means the process begins when a message arrives from the user.
  • The two circles on the edge of Run turn in worker are boundary events. The clock is the 30 minute limit; the envelope is the Stop button. Each interrupts the task and takes its own path.
  • Chat already running a turn? tests one fact with two answers, so it stays a gateway. It is not worth a decision table.
  • Four ends, four outcomes, each named for its result. A single generic "End" would hide that.

Spending limit

BPMN + DMNexamples/spending-limit/
Question
before a Chat turn starts, does the spending limit let it run, run it with a warning, or refuse it?
Notation
both. The process (what happens around the decision) is BPMN; the decision (facts in, action out) is DMN, connected as in bpmn-vs-dmn.md.
Participants
MonoRail app (drawn in full).
Outcomes
Turn finished, Turn refused.
Decisions
"Spending limit action" has four inputs (limit enabled, share spent, over-limit behaviour, one more turn allowed) and three outcomes, so it is extracted to DMN (BL-6, BL-7). Its table is proven complete and exclusive by the linter.

What to notice

  • The table icon marks a business rule task: it asks a decision. The link is written in the file as spending-limit-action.dmn#dec_spendingLimitAction.
  • The gateway's three flows carry exactly the decision's three outputs: allow, warn, stop. The linter compares them with the table.
  • The process says nothing about percentages. All the rules live in the table, so changing a threshold never touches the flow.
  • The requirements diagram shows what the decision needs. The table shows how it decides. The linter proves the table matches every combination of inputs exactly once.

Shapes in these examples

  • Start eventThin circle. An envelope inside means it starts on a message.
  • End eventThick circle. One distinct outcome, named for its result.
  • Service taskRounded box with a gear. Software does it.
  • Business rule taskTable icon. Asks a decision.
  • GatewayDiamond. A question, with its answers on the flows.
  • Sequence flowSolid, filled arrowhead. The order of steps.
  • Message flowDashed, circle at the sender. Between pools.
  • Boundary eventCircle on a task's edge. A limit or interruption.
  • Data storeCylinder. A value that outlives one run.
  • PoolBand on the left. A participant we draw in full.
  • Black-box poolPlain bar. A participant we only talk to.
  • Decision tableDMN. Rules in rows, hit policy letter top left.

The full list of allowed shapes, with what each means and when to use it, is in docs/symbol-reference.md. A style changes colour, type, corner radius and shadow, never a shape, a marker or a line pattern (docs/themes.md); colour in a style only repeats what the shape already says.

Drawing your own

Write the brief first: the question, the trigger, who takes part, every way it can end, the steps, the decisions, the waits and limits. Then write only the meaning of the diagram (elements and flows, no coordinates, no style) and run node tools/diagrams.mjs build <folder>. It checks the rules, adds the layout and writes the SVG in the project's style (diagrams.config.json). AGENTS.md tells an agent exactly this.
